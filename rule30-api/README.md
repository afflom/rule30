<h1 align="center">Centerline</h1>
<p align="center"><em>Every arrow a theorem.</em></p>

`rule30-api` is the LexLean application model of this repository's work on
Wolfram's Rule 30 Prize, Problem 1, and the PrismPM project model around it.
Everything in it is data plus theorems the Lean kernel decides, generated by
`bin/r30 api sync` from the command-line parser, the claim register
(`frontier.toml`) and the model data in `tools/r30/`, and verified by the
same `lexlean verify` as the paper. **Centerline** is the name of the
stakeholder view it renders: the reduction tree, the register, the interface
sheets and the open leaves, published on every push to `main`.

## Modules (`src/`)

| Module | Declares | Decided by the kernel |
| --- | --- | --- |
| `Api.lex.tex` | the `r30` command surface (`Argument`, `Command`, `commands`) | the command count |
| `Register.lex.tex` | the claims of `frontier.toml` | every `depends` target is a claim; every proved claim names a Lean theorem |
| `Architecture.lex.tex` | the conceptual model, stakeholders, concerns, viewpoints, views and the quality model, on prism-stdlib's `Foundation.Arch` and `Foundation.Qual` | the stdlib's index references agree with the labeled ids; every concern is framed by a viewpoint of a stakeholder who holds it; every viewpoint governs a view; every command a view or a measure names is a command of `Api` |
| `Presentation.lex.tex` | the brand, the published artifacts, the panels of the site, the journey of each stakeholder | panels are governed by `Architecture` viewpoints; journeys belong to declared stakeholders; artifacts come from `Api` commands; published paths are distinct |
| `Application.lex.tex` | the application and its publication (the view workflow) | the entry page and the logo are published artifacts; the workflow's timeout is within the quality threshold; the status marks cover every status of `Register` |

`stdlib/Foundation/{Arch,Qual}.lex.tex` and `language/prism.{arch,qual}` are
UOR-Foundation/PrismPM sources (prism-stdlib 0.2.0), migrated to language 1.2
with `lexlean migrate --to 1.2` and vendored with their licenses
(`stdlib/LICENSE-*`, `language/LICENSE-*`). They are a path source root and
two path lexicon sources of `lexlean.toml`; nothing else of PrismPM is a
dependency.

## What "optimal implementation" means here

`Architecture.lex.tex` carries an ISO/IEC 25010 quality model on
`Foundation.Qual`: validation costs time once, in the gate, and never on the
research loop (one module checks in seconds, `verify api` under a minute, CI
renders within five minutes, the gate within half an hour); every module has
one generator and drift is refused (`api check`); nothing unproved is called
proved and no theorem uses an axiom beyond `propext` and `Quot.sound`. Each
measure names the `r30` command that reports it and the threshold it must
stay within, and `Application.lex.tex` decides that the view workflow's
timeout is within the CI threshold.

## The view

```
bin/r30 view render --out view     # the artifacts Presentation.lex.tex declares, with the site
```

`view/index.html` is `site/index.html` with the view data embedded, so the
downloaded artifact opens from disk without a server or a dependency. The
page is one file: dark and light themes, phone width, the tree, the register
with filters and search, the open leaves, the sheets, the modules, the quality
measures and the journeys. The logo, `site/logo.svg`, is Rule 30 itself: the
first twelve rows from a single black cell, the center column in amber; it is
generated by `api sync` like the modules and imitates no one's mark.

## The PrismPM model (`model/`, `schemas/`, `features/`, `CONFORMANCE.md`, `prismpm.toml`)

`authorities`, `ids` and `ledger` (`template/1`) are the register as
capabilities with their evidence; `commands` (`prismpm/command-contract/1`)
is every leaf of the parser with what it mutates and the schema of its
result; `standards` (`prismpm/standards/1`) names ISO/IEC/IEEE 42010 and
ISO/IEC 25010 through the vendored facets with exactly the entries the
architecture uses; `projection` (`prismpm/projection/1`) says which
declaration projects to which collection of the view; `contracts`
(`prismpm/contracts/1`) with `schemas/` describes the JSON the project
publishes: `register.json`, the interface sheets, and the `--json` reports of
`status`, `brief`, `chain`, `claim`, `api check` and `api production`, each a
closed schema the tests validate the live report against. `errors`
(`prismpm/errors/1`) is every typed failure of the commands: `cli.py` exits
only through `errors.fail` with a registered code (`R30nnnn`, exit 1 when a
check failed, 2 when a request was refused), and the tests refuse an
unregistered code or an unused row. `dependencies` (`prismpm/dependencies/1`)
pins the compiler (version and compiler-semantics id), the Lean toolchain,
the builtin lexicons and the vendored prism-stdlib with their tree digests;
`stdlib-package` (`prismpm/stdlib-package/1`) names that stdlib;
`runtime-roots` (`prismpm/runtime-roots/1`) lists the production roots.
`features/suites/<suite>.feature` holds one Gherkin scenario per id of
`ids.toml`, tagged with the id and its level and worded by the level
(`some-true`: reproduced from its authority; `build`: exercised against its
oracle; `open`: measured, never asserted), and `CONFORMANCE.md` is the
register as a document. All of it is generated by `api sync` and checked for
drift by `api check`.

## Rust emission (`production/`, `bin/r30 api production`)

`commands` and `commandCount` of `Api.lex.tex` are production roots (SPEC
§17.13: `executable: true, production: {effects: [allocation], targets:
[rust-std]}`; strings and lists allocate, so only `rust-std` realizes them).
`production/request.json` is the `lexlean/production-request/1` document
generated from them, one crate per root with the pinned target digest of
`lexlean production targets`. `bin/r30 api production` runs `lexlean lock`,
`lexlean production build --request production/request.json` and
`verify-artifact` on the bundle, and reports each package with its
certification (`kernel-checked`: certificates A, B and E compiled under the
pinned Lean, replayed through `leanchecker`, depending on exactly
`Classical.choice`, `Quot.sound` and `propext`) and effects. The bundle is
content-addressed under `.lexlean/production/<result-id>/` and never
committed; `packages/rust-std/rule30_api_commands/` is a Cargo crate whose
`run()` returns the command list, and it builds with a stock `cargo`. The
Python package `tools/r30` remains the interim runtime around the modules.

## Commands

```
bin/r30 api sync                   # regenerate every module, register, schema, feature, CONFORMANCE.md and the logo; lock
bin/r30 api check                  # refuse drift (run by the tests and the gate)
bin/r30 api production             # export the production roots to certified Rust and replay the bundle (about a minute)
bin/r30 api production --targets   # the compiler's target descriptors
bin/r30 verify api                 # lexlean verify of the seven modules (about 25 s)
bin/r30 view render [--out DIR]    # the current view
```
