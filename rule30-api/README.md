<h1 align="center">Centerline</h1>
<p align="center"><em>Every arrow a theorem.</em></p>

`rule30-api` is the LexLean application model of this repository's work on
Wolfram's Rule 30 Prize, Problem 1, and the PrismPM project model around it.
Everything in it is data plus theorems the Lean kernel decides, generated by
`bin/r30 api sync` from the command-line parser, the claim register
(`frontier.toml`) and the model data in `tools/r30/`, and verified by the
same `lexlean verify` as the paper. **Centerline** is the name of the
stakeholder view it renders: the reduction tree, the register, the interface
sheets, the open leaves, the paper's statements and a plain-language guide,
published on every push to `main` at <https://afflom.github.io/rule30/>.

## Modules (`src/`)

| Module | Declares | Decided by the kernel |
| --- | --- | --- |
| `Api.lex.tex` | the `r30` command surface (`Argument`, `Command`, `commands`) | the command count |
| `Register.lex.tex` | the claims of `frontier.toml` | every `depends` target is a claim; every proved claim names a Lean theorem |
| `Architecture.lex.tex` | the conceptual model, stakeholders, concerns, viewpoints, views and the quality model, on prism-stdlib's `Foundation.Arch` and `Foundation.Qual` | the stdlib's index references agree with the labeled ids; every concern is framed by a viewpoint of a stakeholder who holds it; every viewpoint governs a view; every command a view or a measure names is a command of `Api` |
| `Presentation.lex.tex` | the brand, the published artifacts, the panels of the site, the explainer's paragraphs, the open obligation's id, the journey of each stakeholder | panels are governed by `Architecture` viewpoints; journeys belong to declared stakeholders; artifacts come from `Api` commands; published paths and paragraph ids are distinct |
| `Application.lex.tex` | the application and its publication (the view workflow, the Pages environment and URL) | the entry page and the logo are published artifacts; the publication's workflow is the application's; its timeout is within the quality threshold; the obligation is an open claim of `Register`; the status marks cover every status of `Register` |
| `Observer.lex.tex` | the Observer: for every journey of `Presentation`, the object quadruple (`Quadruple`: the problem, the proof as real object, the journey as sensual object, the proved claims its panels render as real qualities, its panels as sensual qualities, the open claims as withdrawn), the `Overlap` and `Interaction` rows between vantages, the `Facet` rows correlating the proof's own vantages, and a declared `gauge` renaming of the panel ids | every vantage is a declared journey and every journey a vantage; the object is the declared problem; real qualities are proved claims, withdrawn ids open claims, sensual qualities the journey's panels; no panel renders a withdrawn claim; every vantage sees part of the real object; interactions are symmetric and through shared panels; the facets are claims of the stated status; the gauge keeps the real qualities and transforms the sensual ones |
| `Convert.lex.tex` | the converter from Lean signatures to LexLean statements (`tools/r30/convert.py`): the signature language (`Node`, `Signature`), a snapshot of the glossary entries the fixtures resolve (`Lexeme`), the operator-class, hint and rewrite tables, and `convert` (`check`, `prop`, `math`, binder naming) as definitions | on 28 real signatures of the research modules (`tools/r30/convert_fixtures.json`), `convert` yields exactly the statement, or the refusal, the Python converter produces; the fixture count |

## The converter in LexLean, and what stays in Python

`Convert.lex.tex` is `convert.py` restated: a Lean type as `bin/r30 sig`
prints it, encoded as a node arena (a binder's type precedes the binder,
which precedes the body, so a binder's name is a pure function of the arena
prefix: `nameAt`), a snapshot of the glossary as `Lexeme` rows (surface,
frame, arity, precedence, associativity, result sort, visibility from
`r30.observation`, the target of `theorem add`): the core connectives and
sorts, and exactly the entries `convert.py` resolves on the fixtures, so
that `theorem add` elsewhere in the glossary never changes the module and
the gate never re-verifies it on the proof loop; and the converter as first-order definitions
with structural recursion on a fuel: `check` raises the refusals of the
first pass in the order Python raises them, `prop` writes the controlled
English, `math` the islands with precedence-aware parentheses. `convert`
returns `Out {ok, text}`, `text` the statement or the refusal as a list of
characters, and `convertsN` decides for each fixture that
`outcome (convert signatureN)` is `"statement"` or `"refused"` followed by
the characters of what `convert.py` says. `bin/r30 api sync --fixtures`
re-captures the fixtures from Lean; `api sync` is the only regenerator, and
`api check` refuses drift: a change to `convert.py`, to a fixture's
statement, or to a glossary entry the fixtures resolve (qid, surface, frame,
arity, precedence, visibility) makes the committed module differ from the
one `api sync` would write.

The boundary, what the pinned LexLean (0.4.0, language 1.2) cannot carry and
Python keeps as the interim runtime:

- **string concatenation.** No constructed `String` is decidable by the
  kernel: `join`, the only string-building primitive, lowers to
  `String.intercalate`, which Lean's module system leaves opaque to
  `decide` and `rfl` (literal strings compare fine). The module therefore
  emits the statement as a list of one-character strings; `convert.py`'s
  `"".join` is the only step between `Out.text` and the statement.
- **reading the s-expression** into the arena (`convertmodel.encode`) and
  the `similar:` candidates of a `no lexeme denotes` refusal, which need
  lower-casing; the quoted excerpt of two refusals (`application of a
  non-constant head`, `cannot translate`); and, in binder names, the
  deletion of characters other than `_`, `✝` and the alphanumerics (`'`
  becomes `prime` in both).
- **the glossary** is in the module only as the snapshot above (a lookup
  of a constant outside it is a `no lexeme denotes` refusal in LexLean
  where Python might resolve it), and the module is specialized to the
  `r30.observation` target.

`convert` is not a production root. The pinned compiler links it as one
(every definition marked `executable`, the root admitting `allocation`,
`overflow` and `recursion`), but `lexlean production build` then stops:
certificate A of the root is 7.3 MB, beyond the project's 4 MB
`max_file_bytes`, and with that limit raised the compiler's own package
manifest exceeds its canonical-JSON recursion limit (LLI9001, after nine
minutes of certification), the module's data being nested lists. Until the
compiler canonicalizes such a manifest, the Python converter stays the
runtime and the module is the kernel-checked specification.

`stdlib/Foundation/{Arch,Qual}.lex.tex` and `language/prism.{arch,qual}` are
UOR-Foundation/PrismPM sources (prism-stdlib 0.2.0), migrated to language 1.2
with `lexlean migrate --to 1.2` and vendored with their licenses
(`stdlib/LICENSE-*`, `language/LICENSE-*`). They are a path source root and
two path lexicon sources of `lexlean.toml`; nothing else of PrismPM is a
dependency.

## The Observer

`Observer.lex.tex` is the object quadruple of object-oriented ontology
(Harman's RO, SO, RQ, SQ, as the UOR framework formalizes it: a withdrawn
real object, the object as it appears from a vantage, qualities invariant
across vantages, qualities that depend on the vantage; `RO·SO` is what a
vantage sees of the real object, objects meet only vicariously through
shared sensual qualities, and an automorphism keeps `RQ` while it transforms
`SQ`) read over what this repository implements. The mapping is data: the
object is the conceptual model of `Architecture` and the real object the root
claim `problem1` (the proof), whose withdrawn core is the open obligation
`aperiodic-compensation` (no view renders a proof of it); each journey of
`Presentation` is a sensual object; the real qualities a journey sees are the
proved claims its panels render (a panel presenting the tree, the register or
a register module renders every proved claim; the interface sheets render the
selected claim with the proved chain above it, the open leaves being what a
sheet is written for; the open-leaves panel renders only withdrawn claims),
the sensual qualities are its panels, the withdrawn ids the open claims; two
vantages interact through the panels they share. The proof itself is
cross-correlated as `Facet` rows, never as theorems about the automaton: the
regular side of the pattern is a vantage from which the center shows sensual
qualities (`edge-parity`, `three-diagonal-band`, `left-band`), the deep
interior is the withdrawn core (`aperiodic-compensation`; withdrawal is the
measured non-collapse of the diagonals of index at least three), and the
proved reductions of the root are the real qualities under the kernel. The
kernel decides the theorems the table above lists, among them `withdrawal`,
`everyVantageSeesTheObject`, `interactionsAreSymmetric` and the gauge
covariance `gaugeKeepsRealQualities` / `gaugeTransformsSensualQualities`.
`tools/r30/observermodel.py` derives every row from the register and from
the stakeholders, journeys, panels and artifacts of `archmodel` and
`presentationmodel` at `api sync` (nothing is copied), writes the same rows to
`model/observer.toml`, and `api check` refuses drift.

## What "optimal implementation" means here

`Architecture.lex.tex` carries an ISO/IEC 25010 quality model on
`Foundation.Qual`: validation costs time once, in the gate, and never on the
research loop (one module checks in seconds, `verify api` a few minutes, CI
renders within five minutes, the gate within half an hour); every module has
one generator and drift is refused (`api check`); nothing unproved is called
proved and no theorem uses an axiom beyond `propext` and `Quot.sound`. Each
measure names the `r30` command that reports it and the threshold it must
stay within, and `Application.lex.tex` decides that the view workflow's
timeout is within the CI threshold.

## The view

```
bin/r30 view render --out view     # the artifacts Presentation.lex.tex declares, with the site
```

`view/index.html` is `site/index.html` with the view data embedded, so the
downloaded artifact opens from disk without a server or a dependency. The
page is one file: dark and light themes, phone width, the Rule 30 picture,
the plain-language explainer, the tree, the register with filters and search,
the open leaves, the paper's statements, the open obligation, the refuted
routes, the sheets, the modules, the quality measures and the journeys. The
logo, `site/logo.svg`, is Rule 30 itself: the first twelve rows from a single
black cell, the center column in amber; it is generated by `api sync` like
the modules and imitates no one's mark.

## The views and the Pages deployment

The site is not arbitrary: `Architecture.lex.tex` declares the stakeholders
and the concerns each holds, a viewpoint frames each concern, and every panel
of `Presentation.lex.tex` is governed by one of those viewpoints and belongs
to a journey (`panelsGovernedByViewpoints`, `everyPanelInAJourney`, decided
by the kernel). Four readings of the one page:

| Stakeholder | Journey | Panels |
| --- | --- | --- |
| the researcher (developer view) | `research-session` | open leaves, interface sheets, quality |
| the UOR Foundation (machine view) | `stdlib-feedback` | LexLean modules, quality |
| the mathematician | `mathematics` | paper, reduction tree, open obligation, refuted routes, register |
| the layperson | `first-visit` | Rule 30 (the picture), in plain words, reduction tree |

The mathematician's panels read `statements.json`, which `view render`
generates from `rule30-paper/src/Observations.lex.tex` and the glossary:
every theorem, lemma and corollary in the paper's controlled English with
its section, the lexeme its proof closes the goal with, and that entry's Lean
name and module; plus the attested PDFs (`Rule30-Paper.pdf`,
`Rule30-Observations.pdf`, `Rule30-Core.pdf`, copied beside the site with
`pdf-manifest.json` and its SHA-256 digests) and the identifiers of the
paper's latest accepted attestation (`rule30-paper/verified-latest`). The
open obligation (`obligation` in `Presentation.lex.tex`; `obligationIsOpen`
in `Application.lex.tex` decides it is an open claim of the register) and the
refuted routes with their Lean refutation or experiment are read from
`register.json`. The layperson's panels read `rule30.svg` (the first 48 rows,
the center column highlighted; the site inlines the same drawing with its
colour tokens) and `explainer.json`, the paragraphs `Presentation.lex.tex`
declares as data (`explainer`), which the tests keep free of formal
vocabulary.

`.github/workflows/view.yml` is the publication `Application.lex.tex`
declares. It renders the view (`python3 -m tools.r30 view render --out
view`), keeps it as the `rule30-current-view` artifact, uploads it with
`actions/upload-pages-artifact` and deploys it with `actions/deploy-pages`
in the `github-pages` environment (`contents: read`, `pages: write`,
`id-token: write`; concurrency group `pages`) to
<https://afflom.github.io/rule30/>, then fetches the deployed page and checks
that the commit it embeds (`"commit"` in the view data) is `GITHUB_SHA`. It
runs no Lean, no lexlean and no tests: validation happened in the pre-commit
gate, and the workflow's five-minute timeout is decided against the quality
model (`publicationWithinBudget`).

## The PrismPM model (`model/`, `schemas/`, `features/`, `CONFORMANCE.md`, `prismpm.toml`)

`authorities`, `ids` and `ledger` (`template/1`) are the register as
capabilities with their evidence; `commands` (`prismpm/command-contract/1`)
is every leaf of the parser with what it mutates and the schema of its
result; `standards` (`prismpm/standards/1`) names ISO/IEC/IEEE 42010 and
ISO/IEC 25010 through the vendored facets with exactly the entries the
architecture uses; `projection` (`prismpm/projection/1`) says which
declaration projects to which collection of the view; `contracts`
(`prismpm/contracts/1`) with `schemas/` describes the JSON the project
publishes: `register.json`, the interface sheets, and the `--json` reports of
`status`, `brief`, `chain`, `claim`, `api check` and `api production`, each a
closed schema the tests validate the live report against. `errors`
(`prismpm/errors/1`) is every typed failure of the commands: `cli.py` exits
only through `errors.fail` with a registered code (`R30nnnn`, exit 1 when a
check failed, 2 when a request was refused), and the tests refuse an
unregistered code or an unused row. `dependencies` (`prismpm/dependencies/1`)
pins the compiler (version and compiler-semantics id), the Lean toolchain,
the builtin lexicons and the vendored prism-stdlib with their tree digests;
`stdlib-package` (`prismpm/stdlib-package/1`) names that stdlib;
`runtime-roots` (`prismpm/runtime-roots/1`) lists the production roots;
`observer` (`r30/observer/1`) is the rows of `Observer.lex.tex`.
`features/suites/<suite>.feature` holds one Gherkin scenario per id of
`ids.toml`, tagged with the id and its level and worded by the level
(`some-true`: reproduced from its authority; `build`: exercised against its
oracle; `open`: measured, never asserted), and `CONFORMANCE.md` is the
register as a document. All of it is generated by `api sync` and checked for
drift by `api check`.

## Rust emission (`production/`, `bin/r30 api production`)

`commands` and `commandCount` of `Api.lex.tex` are production roots (SPEC
§17.13: `executable: true, production: {effects: [allocation], targets:
[rust-std]}`; strings and lists allocate, so only `rust-std` realizes them).
`production/request.json` is the `lexlean/production-request/1` document
generated from them, one crate per root with the pinned target digest of
`lexlean production targets`. `bin/r30 api production` runs `lexlean lock`,
`lexlean production build --request production/request.json` and
`verify-artifact` on the bundle, and reports each package with its
certification (`kernel-checked`: certificates A, B and E compiled under the
pinned Lean, replayed through `leanchecker`, depending on exactly
`Classical.choice`, `Quot.sound` and `propext`) and effects. The bundle is
content-addressed under `.lexlean/production/<result-id>/` and never
committed; `packages/rust-std/rule30_api_commands/` is a Cargo crate whose
`run()` returns the command list, and it builds with a stock `cargo`. The
Python package `tools/r30` remains the interim runtime around the modules.

## Commands

```
bin/r30 api sync                   # regenerate every module, register, schema, feature, CONFORMANCE.md and the logo; lock
bin/r30 api check                  # refuse drift (run by the tests and the gate)
bin/r30 api production             # export the production roots to certified Rust and replay the bundle (about a minute)
bin/r30 api production --targets   # the compiler's target descriptors
bin/r30 verify api                 # lexlean verify of the nine modules (about five minutes; Convert.lex.tex decides 28 conversions)
bin/r30 view render [--out DIR]    # the current view (the site, statements.json, explainer.json, rule30.svg, the PDFs)
```
