# v0.2 release qualification

Status: provisional. This document does not announce a release or qualify an
implementation. Problem 1 remains unproved. The existing v0.1 assets retain their
original identities and proof policies.

## Mathematical assets

Retain the paper and core PDFs (including their existing aliases), generated
Lean and TeX, Observations PDF/Lean/TeX, paper/core attestations, lockfiles,
complete verified archives and SHA256SUMS. The unchanged acceptance gate remains
mandatory. The download-smoke job checks required files, checksum coverage,
PDF alias equality and archive readability using a downloaded workflow artifact
without a source checkout. It is a transport/package check, not a kernel replay
or a test of public GitHub Release downloads.

Checksum records must use lowercase SHA-256 digests and flat asset names. Path
traversal, absolute paths, hidden files, directories and symlinks are rejected
before checksum-controlled file access; checksum coverage rejects duplicate or
unlisted assets.

## Native contract awaiting the implementation owner

The implementation owner must confirm the final executable inventory, production
requests, accepted source commit, bundle layout, supported verifier invocation,
and deterministic consumer fixtures. Existing request files describe research
attempt/cohort and environment commands; they do not establish the final v0.2
inventory or acceptance of the unpublished coordinator.

The proposed native distribution contains the confirmed executables, complete
certified production bundles, requests/examples, licenses and a manifest binding
source commit, compiler identity, target identity, platform and file hashes.
Names and paths must come from accepted outputs, not inferred interfaces.
Package only platforms that have passed consumer tests. No Windows, macOS, ARM,
browser or Holo runtime support is claimed by this proposal. Record the actual
OS/architecture, runtime libraries and external proof-tool prerequisites for each
qualified binary. A production certificate alone does not certify distributed
machine code; the build provenance and consumer tests must connect that binary
to the certified generated package.

## Required integration before publication

1. Obtain the implementation owner's accepted native contract and final source
   revision. Keep the unchanged proof gate and its complete obligation closure.
2. Build the native artifacts from that revision, retain production verification
   and build provenance, and include all files in the release checksum inventory.
3. In a clean consumer job, download and extract the candidate distribution,
   verify its inventory/hashes, replay certificates with the supported verifier,
   and run every executable's documented help, invalid-input and deterministic
   success fixtures. Supply only documented prerequisites; do not rely on the
   source checkout or a developer cache. Retain passed and failed evidence.
4. Replace the workflow's explicit v0.2 publication blocker with dependencies on
   these successful qualification jobs. Do not remove it solely because the
   mathematical download checks passed. Extend the publication asset list with
   the confirmed native outputs and preserve every mathematical asset.
   The current blocker is a temporary representation of missing native evidence,
   not a permanent ban on v0.2. Replace it in the same reviewed change that wires
   the confirmed artifacts and successful consumer jobs; no manual readiness flag
   or workflow input may substitute for those job results. Its tag match covers
   v0.2, v0.2 patch releases and prereleases, not unrelated versions such as v0.20.
5. Publish only the qualified bytes. Check their public downloads and hashes,
   reporting post-publication transport results separately from pre-publication
   qualification. Never label a pending check as passed.

## Ownership and limits

Release-readiness work owns `.github/workflows/release.yml`, the README release
sections and this document. The implementation owner owns coordinator/intake
sources, production requests, generated modules, proof fixtures and final native
acceptance. Coordinate those boundaries before integration. No new application
logic belongs in workflow glue, Python or shell packaging scripts.

Issue #8 is a later distribution opportunity, not a v0.2 prerequisite. Current
native process/filesystem commands have not been qualified for Holo Search.
A portable application needs its own explicit model, runtime support and verified
acceptance; the rendered site and published vectors do not establish that support.
Do not execute third-party bootstrap instructions merely because an issue suggests
them, or describe registry indexing as proof of application correctness.
